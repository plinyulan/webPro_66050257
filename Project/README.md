# 🍲 Suki House — ระบบจัดการออร์เดอร์ร้านสุกี้

Final Project หัวข้อที่ 1 · React 18 + Vite + React Router · ไอคอน: Lucide · Backend: Node.js (Express + json-server)

## วิธีรัน

```bash
npm install          # ครั้งแรกครั้งเดียว
npm run dev          # รัน backend (:3001) + frontend (:5173) พร้อมกัน
```

เปิด <http://localhost:5173> · หยุดด้วย `Ctrl + C`

## การทำงานตามลำดับ (ตามโจทย์)

1. ลูกค้านั่งโต๊ะ A05 → สแกน QR → เปิด `/table/A05`
2. ระบบแสดงเมนูทั้งหมดแยกหมวด (เนื้อสัตว์ ทะเล ลูกชิ้น ผัก เส้น เครื่องดื่ม)
3. ลูกค้าเลือกอาหาร ปรับจำนวน เพิ่มลงตะกร้า (ตะกร้าจำไว้แม้รีเฟรชหน้า)
4. กด **สั่งอาหาร** → **ยืนยันการสั่งอาหาร**
5. เซิร์ฟเวอร์ตรวจโต๊ะ ตรวจเมนูว่ายังไม่หมด **คำนวณราคาเอง** แล้วบันทึกออร์เดอร์พร้อมเลขโต๊ะ วันเวลา รายการอาหาร
6. หน้า Dashboard พนักงานได้รับแจ้งผ่าน **Server-Sent Events** → ออร์เดอร์ใหม่ขึ้นทันที (ไม่ต้องรีเฟรช) พร้อมแจ้งเตือน
7. พนักงานเปลี่ยนสถานะ: รอรับออร์เดอร์ → กำลังเตรียมอาหาร → เสิร์ฟแล้ว
8. หน้าลูกค้าอัปเดตแถบสถานะเองทันที
9. ลูกค้ากด “เช็กบิล” → พนักงานกด “ปิดบิล” → ลูกค้าเห็น “ชำระเงินเรียบร้อย” และบิลเข้าประวัติ

**หลักการสำคัญ:** ออร์เดอร์ทั้งหมดอยู่ที่เซิร์ฟเวอร์ (`server/db.json`) ทุกหน้าจอเห็นข้อมูลชุดเดียวกัน เครื่องลูกค้าเก็บแค่ *ตะกร้าที่ยังไม่สั่ง* ใน localStorage

## สถาปัตยกรรม

```
มือถือลูกค้า ─┐                         ┌─ REST  /api/*      (อ่าน/เขียนข้อมูล)
              ├─► React (Vite :5173) ───┤
คอมพนักงาน ──┘                         └─ SSE   /api/events (แจ้งว่า resource ไหนเปลี่ยน)
                                                  │
                               Node.js server (:3001) ── server/db.json
```

- **Real-time:** เมื่อมีการเขียนข้อมูล เซิร์ฟเวอร์ส่ง `{resource:"orders"}` ไปทุกเครื่องผ่าน SSE → hook `useApi` ที่สนใจ resource นั้นโหลดข้อมูลใหม่ (+ polling 15 วินาทีสำรองถ้าการเชื่อมต่อหลุด, มีไฟ 🟢 Live บอกสถานะ)
- **ความปลอดภัย:** รหัสผ่านเก็บแบบ hash (scrypt + salt) · token สุ่ม 256-bit หมดอายุ 12 ชม. · `/api/users` และ `/api/db` ถูกปิด · ทุกการเขียนตรวจสิทธิ์ที่ server (ซ่อนปุ่มฝั่ง client อย่างเดียวไม่พอ)
- **ไม่เชื่อข้อมูลจากลูกค้า:** ลูกค้าส่งแค่ `menuId + qty` เซิร์ฟเวอร์ดึงราคาจริงมาคำนวณเอง, ตัด field แปลกปลอมทิ้ง

## สคริปต์สาธิต (~7 นาที)

1. `npm run reset-db` → `npm run dev`
2. เปิด 2 หน้าต่างคู่กัน: ซ้าย = ลูกค้า `/table/A05` (DevTools โหมดมือถือ), ขวา = พนักงาน `/staff`
3. ฝั่งพนักงาน: ลองรหัสผิด → error, แล้วล็อกอิน `staff`
4. ฝั่งลูกค้า: ค้นหา “หมู”, กรองหมวด, เพิ่มลงตะกร้า, ใส่หมายเหตุ, ยืนยันสั่ง
5. ชี้ให้ดูว่าออร์เดอร์ **ขึ้นฝั่งพนักงานทันที** + toast แจ้งเตือน
6. พนักงานกด “กำลังเตรียม” → ฝั่งลูกค้าแถบสถานะเปลี่ยนเอง
7. ลูกค้าสั่งเพิ่มอีกรายการ แล้วกดยกเลิก (ยังรอรับ → ยกเลิกได้)
8. พนักงาน: เมนู → ปิดการขาย “ชาเย็น” → ฝั่งลูกค้าขึ้น “หมด” ทันที
9. พนักงานกด “เสิร์ฟแล้ว” → ลูกค้ากด “เช็กบิล” → พนักงานกด “ปิดบิล” → ลูกค้าเห็นขอบคุณ
10. ล็อกอิน `manager` → เพิ่มเมนูใหม่ (ลองกรอกผิดให้เห็น validation) → เพิ่มโต๊ะ → โชว์ QR → ประวัติบิล
11. ปิดท้าย: `npm test` (43 ผ่าน) และย่อหน้าต่างให้เห็น responsive

## คำถามที่น่าจะโดนถาม

- **ทำไมต้องมี backend ไม่เก็บใน React state?** — state อยู่ในเบราว์เซอร์เครื่องเดียว มือถือลูกค้ากับคอมพนักงานคนละเครื่องจึงต้องมีที่เก็บกลาง
- **Real-time ทำงานอย่างไร?** — Server-Sent Events: เบราว์เซอร์เปิดการเชื่อมต่อค้างไว้ที่ `/api/events` เซิร์ฟเวอร์ push ชื่อ resource ที่เปลี่ยน แล้ว `useApi` โหลดใหม่ ใช้ SSE แทน WebSocket เพราะข้อมูลไหลทางเดียว (server → client) และเบราว์เซอร์ต่อใหม่ให้เอง
- **ทำไมใช้ `useReducer` กับตะกร้า?** — มีหลาย action (ADD / SET_QTY / REMOVE / CLEAR) รวม logic ไว้ที่เดียว และเป็น pure function ทดสอบได้ง่าย
- **`useMemo` ใช้ทำไม?** — กรอง/เรียงเมนูและคำนวณสถิติใหม่เฉพาะเมื่อข้อมูลหรือคำค้นเปลี่ยน ไม่คำนวณทุกครั้งที่ re-render
- **`useRef` ใน Dashboard ใช้ทำไม?** — จำ id ออร์เดอร์ที่เคยเห็นแล้ว เพื่อรู้ว่าอันไหน “ใหม่” โดยไม่ทำให้ re-render
- **ป้องกันลูกค้าแก้ราคาอย่างไร?** — client ส่งแค่ menuId + จำนวน, server ดึงราคาจากฐานข้อมูลเอง
- **ถ้าเน็ตหลุด?** — `useApi` แสดง error + ปุ่มลองใหม่, SSE ต่อใหม่อัตโนมัติ, มี polling สำรอง
- **ทดสอบอย่างไร?** — Vitest: reducer/utils (pure), component (Testing Library + jsdom), API (supertest ใช้ฐานข้อมูลสำเนาใหม่ทุกเทสต์), E2E (Playwright คุม Chrome จริงทั้งลูกค้าและพนักงานพร้อมกัน)

## ข้อจำกัด (ตอบตรง ๆ ถ้าโดนถาม)

- ฐานข้อมูลเป็นไฟล์ JSON เหมาะกับร้านเดียว/งานสาธิต ถ้าใช้จริงหลายสาขาควรย้ายไป PostgreSQL หรือ Firebase
- session เก็บในหน่วยความจำเซิร์ฟเวอร์ → รีสตาร์ตเซิร์ฟเวอร์แล้วพนักงานต้องล็อกอินใหม่
- ไม่มีระบบชำระเงินออนไลน์ (ปิดบิล = พนักงานยืนยันว่ารับเงินแล้ว)
